## Data and timestamp contract

1. Source-current V304 priority `no_indexed_image` only: canonical `motion_<13digits>.mp4` in S9 microSD original archive, 3840x2160, manifest SHA-256 and byte size, catalog revision, native extraction pass, pinned YuNet model SHA `8f2383e4…552fa4`, queue active/processing lease and current quality-priority. SAME-YuNet no-supported-face `blocked` rows remain deliberately unresolved.
2. In each of exactly three original-source-relative offsets (at 1/6, 1/2 and 5/6 video duration), the C720P controller rechecks existing camera/thermal/worker-lock policy, separately enrolled Android memory/SD/PID/DEX JAR hash, authoritative source report/catalog/revision/model and remaining queue lease. It invokes one fixed, hash-attested `adb shell ... /system/bin/app_process` class per frame, sequentially, with 65s per call, 195s sequence ceiling and >=40s queue-lease reserve. The application cannot silently launch background jobs or upload media.
3. **Actual presentation timestamps**: `S9Original4KTimedDecoderV371` decodes on the phone with `MediaExtractor` + `MediaCodec`; `BufferInfo.presentationTimeUs` is the actual output timestamp, rather than the prior `MediaMetadataRetriever.getFrameAtTime` request. It decodes 3840x2160 YUV420 into an in-memory bitmap, refusing unsupported image geometry, inaccurate frame PTS, long seeks and deadline exhaustion. Coordinator accepts only an actual decoded presentation time from the `mediacodec_output_buffer_info` source, at/after the requested offset and within 500ms, with three increasing *different* timestamps, valid 4K dimensions and bounded detector candidates.
4. YuNet is pinned and processed on S9 using full original scene + six overlapping native-frame tiles. Padded 640x640 ONNX boxes/eyes are mapped to original 3840x2160 coordinates *before* quality checks and deduplication. Results contain no face image/vector or identity information. The phone returns a single-frame `s9_original4k_phone_frame_probe_v370` receipt with `eligible_to_publish:false`, `host_attestation_required:true` and original source SHA/revision, model, exact decoded PTS, native boxes/count and zero assignments.
5. `s9_phone_gap_coordinator_v371.coordinate()` holds three receipts exclusively in process memory; any changed original, priority, model, recorder PID, low phone memory/SD, unexpected PTS, duplicated/missing frame, timeout or transport failure raises a refusal **without producing any record**. Only a complete three-frame source-qualified record is returned to **existing** V304 `publish` (atomic/private secondary quality report) then to the actual V369 HTTP reader and independent V361 `consumer_visible`. Existing V304 `work()` alone marks completed with ack after V361 200 and persists the queue transaction; it never treats a partial report as complete. A post-completion V361 GET must obtain its fresh clip-scoped revision.
6. **Interruption/recovery:** transient phone failures go through V304 `phone_first_recoverable_deferred` with bounded backoff, zero claimed model-negative result and no retained partial frames. Source revocation is rejected, not retried. If the process crashes during processing, existing V304 lease recovery enforces bounded attempts (<=3) and no hot-loop. A partial secondary report from a prior publication interrupted before consumer acknowledgement does not grant eligibility once queue is pending/rejected; its reader still checks active processing/completed lease and current source on every read.
7. Current qualified completed queue rows stay active; obsolete completed records may enter immutable retirement history only **after** their source priority was withdrawn, after which V361 must return 410. There is no new historic-valid-completed consumer contract, no re-enrollment of retired IDs and no identity-based heuristic.
