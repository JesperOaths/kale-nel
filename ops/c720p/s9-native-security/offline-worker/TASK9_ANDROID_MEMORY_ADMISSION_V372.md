## What can be proven from current source without inference

`S9Original4KTimedDecoderV371.yuv()` processes 3840x2160 = **8,294,400 pixels**. Its full-size `int[] argb` holds 33,177,600 bytes (31.64 MiB), while `Bitmap.createBitmap(argb,...ARGB_8888)` needs another 33,177,600 bytes of pixel storage. This is **66,355,200 bytes (63.28 MiB)** of full-frame allocations across conversion, before codec image buffers or any ONNX Runtime native workspace; it is **not** a total peak bound. `MediaCodec` can hold multiple vendor-allocated, stride-aligned 4K YUV420 buffers (a minimally packed 4K YUV420 frame is 12,441,600 bytes / 11.87 MiB). Number, alignment and residency of buffers cannot be inferred from Java source. A 3840x2160 `Bitmap.createBitmap` full-frame crop may require up to one additional 33,177,600-byte allocation; do not assume Android always aliases it.

Per YuNet 640x640 tile, `bgr()` creates a 409,600-int pixel array (1,638,400 bytes, 1.56 MiB) and a 1,228,800-float BGR tensor (4,915,200 bytes, 4.69 MiB). `Bitmap.createBitmap` produces a padded 640x640 bitmap (1,638,400 bytes) and a resized bitmap of at most that size; `OnnxTensor.createTensor` may copy its Java float array into additional native memory. The seven full/tiled passes are **sequential** in source, not seven simultaneous sessions; nevertheless unreachable Java arrays need not be reclaimed until GC and ORT default native arena/prepacked weights, intermediate activations and 12 output heads have no source-proven upper limit. One pinned ONNX model is <512 kB on disk, but that size says nothing about ORT execution peak RSS/PSS. The 28,515,295-byte AAR is a package size, not a valid RAM estimate. `OrtSession.SessionOptions` sets both thread counts to 1, **does not disable its default CPU arena**. `app_process` per-frame, 65s bounded, can outlive an ADB timeout; orphan-process exclusion is mandatory. `-Xmx` would bound only managed heap, **not** codec/native ORT allocations.

**Conclusion:** >63 MiB known conversion allocations plus codec/ORT/native/GC overhead, **no defensible numerical minimum phone MemAvailable kB yet**. Neither S9 nominal device RAM nor the unrelated >=900 MiB **C720P** guard is a valid Android floor. A guessed positive number in the V371 manifest is prohibited.

Any failure ends qualification here with no Android allocation/inference. Re-evaluate all gates before each later step. Never stop Camera2, voice or HA to manufacture headroom.
